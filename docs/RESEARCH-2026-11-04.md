synthetic fixtures. The artifacts remained under `/tmp`; this did not add firmware to the repository or mutate the
corpus/database.

Both graphs now recover the formerly failed reachable target while remaining explicitly bounded at eight
functions. radare2 6.0.5 and 6.2.4 do not decode the target's exact ratified Zbs `bset` and Zba
`sh1add`/`sh2add`/`sh3add` opcodes. FirmLab therefore creates a local 4 KiB maximum analysis view, replaces only
those exact non-control-flow encodings with same-length RV32 NOPs, asks radare2 for control-flow structure, and
restores the original bytes and mnemonics in the result. The source image is never modified; substitution count
and evidence remain visible, and the result does not claim instruction semantics. Encodings and masks were checked
against RISC-V International's `riscv-opcodes` output and the ratified bit-manipulation specification:
<https://github.com/riscv/riscv-opcodes> and <https://github.com/riscv/riscv-bitmanip>.

The real `nuke_universal` sample also exposed signed negative relative storage
offsets in `LOAD_MAP`. Core now sign-extends them before the API maps storage bytes, while absolute storage
addresses remain unsigned.

## FreeRTOS runtime matrix revalidation

`apps/api/scripts/rtos-freertos-layout-matrix.sh` rebuilt the local FreeRTOS V11.1.0 STM32F4 fixture and passed all
12 supported runtime layouts: 16/32/64-bit `TickType_t`, mini list item enabled/disabled and list-integrity words
enabled/disabled. Every case ran in the `firmlab-firmware:latest` container with `--network none`, booted under
Renode, captured the 256 KiB SRAM region and corroborated the exact known occupants:

- ready: `IDLE` priority 0 and `SpinA`/`SpinB` priority 1;
- delayed: `Sleeper` priority 2;
- suspended: `Parked` priority 3, `QueueRx` priority 4 and `QueueTx` priority 2;
- ordered queue receive wait: `QueueRx` priority 4, priority key 1, with the exported `List_t` pointer independently
  matching `Queue_t + 16 + sizeof(List_t)` and its node matching `TCB.xEventListItem`;
- ordered queue send wait: `QueueTx` priority 2, priority key 3, with a second exported `List_t` pointer independently
  matching `Queue_t + 16` and its node matching `TCB.xEventListItem`;
- `pxCurrentTCB`: one of the two priority-1 spinners;
- `uxTopReadyPriority`: value 1, agreeing with the complete ready-list array;
- integrity-enabled layouts: all 51 or 62 reached `0x5a` markers matched, depending on list layout.

The result deliberately remained `needs_runtime_reproduction` and aggregate coverage remained `partial` because
`xTasksWaitingTermination` was unresolved. Renode refused the platform's remote SVD URL while offline and completed
without it; the test did not claim to measure behavior the SVD might have changed. Tick64 uses the official
`ARM_CM4F` port: application/kernel compile with soft float and only `port.c` with softfp, avoiding FPU instructions
before the port enables the FPU. The V11.1.0 `heap_4.c` conversion warning from 64-bit `portMAX_DELAY` to 32-bit
`size_t` remains visible; the affected stats function is not used by the fixture.

## Runtime/hardware boundaries

- No STM32N6570-DK or ST-LINK device was present in `lsusb`, so no hardware RAM snapshot was produced. The host's
  stock OpenOCD 0.12.0 also has no STM32N6 target scripts; the next capture requires the board plus ST's OpenOCD
  fork/STM32CubeIDE tooling. The official board integrates STLINK-V3EC, but link-time symbols remain the only current
  evidence for the local ST ELF.
- Local `firmlab-firmware:latest` has Renode 1.16.1 and no RP2350/Hazard3 platform. Renode 1.17.0 accepts the full
  Pico SDK ISA string, but upstream still has no RP2350 platform. Offline experiments reached boot-ROM lookup in
  `hello_universal`, and RESETS then USB/CLOCKS/XOSC in `nuke_universal`; those are bounded runtime leads, not a
  peripheral-behavior confirmation. The product now emits a pure, persisted-optional RP2350 runtime plan for the
  selected executable PICOBIN definition: exact file/runtime mapping, minimum Renode 1.17.0, the Pico SDK ISA
  `rv32ima_zicsr_zifencei_zba_zbb_zbs_zbkb_zca_zcb_zcmp`, isolated guest networking, an operator-supplied boot ROM,
  local platform description, required RESETS/XOSC/CLOCKS/TIMER/UART models, and `stop-and-report` for unknown MMIO.
  Both official samples correctly remain `blocked_by_platform`; this is an executable contract scaffold, not a boot
  claim. ISA flags were cross-checked against Raspberry Pi's current Pico SDK toolchain configuration:
  <https://github.com/raspberrypi/pico-sdk/blob/master/cmake/preload/toolchains/pico_riscv_gcc_zcb_zcmp.cmake>.
