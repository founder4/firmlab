# Research lines — 2026-11-03

This note records the primary-source basis, experiments and proof limits behind the 2026-11-03 research slice.
It is not a claim about any firmware image in the corpus.

## AFL++ network harness

Primary source: AFL++'s pinned [`utils/libaflppdesock`](https://github.com/AFLplusplus/AFLplusplus/tree/stable/utils/libaflppdesock)
source and README in the `firmlab-tools:latest` image. The
helper requires `DESOCK_PORT`; `DESOCK_FORK=1` and `DESOCK_CLOSE_EXIT=1` make one-input-per-process operation
explicit.

Observed in a disposable `--network none` tools container:

- the helper compiled successfully and declared `libc.so.6` as a dynamic dependency;
- a synthetic C TCP server on port 8080 received its testcase through stdin under the preload;
- absent and wrong ports timed out;
- a Python server crashed under the same host-built preload.

Conclusion: matching the ELF architecture is necessary but not sufficient. FirmLab now requires an explicit
port and an operator ABI-compatibility assertion before loading the helper. This establishes an input channel; it
does not establish coverage of a firmware protocol parser. Prebuilt architecture/libc pairs and a real firmware
daemon run remain pending.

## Sercomm/Netgear prefix

Primary source: OpenWrt firmware-utils [`src/mksercommfw.c`](https://git.openwrt.org/project/firmware-utils/plain/src/mksercommfw.c)
(observed source revision
`b2a93c6f77bac3a6525e93b383c987b073b4633b`). The generator defines a 512-byte prefix with two `sErCoMm`
markers, version `00 01 00 00`, NUL-padded hardware fields, a big-endian software version, zero reserved padding
and a final byte that makes the complete-image 8-bit sum zero.

The official generator was compiled and run over a synthetic 1 KiB payload. The resulting 1,536-byte image had
the expected fields and a zero complete-image sum. `parseSercommPrefixHeader` and the `sercomm-prefix` signature
implement only this prefix variant. A valid structure with a broken sum is `consistent`; a recomputing sum is
`verified`; malformed declared structure is rejected.

Limits: no real local sample was available; a read-only scan of every local image found no `sErCoMm` marker in the
first 4 KiB. The footer mode, newer Sercomm formats and encryption are not covered. The 8-bit sum proves format
consistency, never provenance, authenticity or adversarial integrity.

No firmware was downloaded. A concrete official candidate for a future real-prefix check is NETGEAR R6020
`R6020-V1.0.0.42.zip` from the [NETGEAR support article](https://kb.netgear.com/000061159); OpenWrt's official
`target/linux/ramips/image/mt76x8.mk` maps R6020 factory images through `netgear_sercomm_nor`/`mksercommfw`.

## FreeRTOS list layouts

Primary sources: FreeRTOS-Kernel V11.1.0 [`include/list.h`](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/V11.1.0/include/list.h)
plus the current official [`list.c`](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/main/list.c),
[`FreeRTOS.h`](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/main/include/FreeRTOS.h) and
[`projdefs.h`](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/main/include/projdefs.h).

Confirmed semantics:

- `configUSE_MINI_LIST_ITEM` defaults to 1; at 0 the sentinel is a full `ListItem_t`;
- `configUSE_LIST_DATA_INTEGRITY_CHECK_BYTES` defaults to 0 and, when enabled, adds `TickType_t` integrity words
  around list/list-item structures according to the official macros;
- the marker value is a repeated `0x5a` pattern at the `TickType_t` width.

FirmLab now derives all mini/integrity layouts from one pure function for explicitly declared 16-, 32- and 64-bit
`TickType_t`. API and UI declare the options; old requests retain 32-bit ticks and defaults mini=1/integrity=0. Tick
values above JavaScript's safe-integer limit remain exact decimal strings. The marker words are read at the declared
width: every list reports attempted, completed and mismatching repeated-`0x5a` checks, and
the API aggregates those counters across all walked lists. A mismatch is evidence of a wrong declared layout or
a torn/corrupt snapshot; it never changes traversal coverage or raises the fixed `needs_runtime_reproduction`
proof state. Persisted result fields remain optional so pre-change jobs still render.
The panel exposes the same counters per lane. Its DOM/type tests pass; a real-browser visual pass was attempted on
2026-11-03 but no browser instance was connected to the session, so responsive visual QA remains pending.

F4 now carries the resolved `uxTopReadyPriority` address from the ELF into the snapshot form, while requiring the
operator to declare whether the build stores a priority (generic selection) or a bitmap (port-optimized selection).
Only a fully resolved, completely walked `pxReadyTasksLists` array licenses a comparison. Manual or partial lists
still allow the scalar read but produce no expected value. Agreement or disagreement is an annotation and never
changes task coverage or the fixed `needs_runtime_reproduction` proof state.

F5 extends that same contract through core, API and panel without inferring tick width from `sizeof(List_t)`.
Compiler-layout checks showed that the differing 32-bit-ABI alignment of `uint64_t` does not change these list
structures, so no inert ABI-alignment selector was added. The V11.1.0 ARM_CM3 fixture now runs 16/32-bit ticks across
all mini/integrity combinations: all eight offline Renode runs recovered the expected tasks, corroborated
`uxTopReadyPriority=1`, and (when enabled) read all 37 or 46 declared integrity markers without mismatches. That
official port rejects 64-bit ticks, so 64-bit support currently has byte/layout tests but no runtime-fixture claim.

The fixture build is now parameterized without replacing the tracked ELF. A single temporary build produced all
four V11.1.0 variants and four offline Renode runs passed end to end: mini/integrity `0/0`, `0/1`, `1/0`, `1/1`
reported real `sizeof(List_t)` values 28, 44, 20 and 32 bytes respectively and recovered exactly the expected
ready, delayed and suspended tasks. Every result remained `needs_runtime_reproduction`.

### Team firmware sample validation

The 15 firmware files already stored in the team volume were exercised offline through disposable containers with
the volume mounted read-only and networking disabled. Current static analysis completed for all 15 without an
exception. Relevant provider-level evidence was:

- both Xiaomi repeater dumps produced the expected eCos monolith finding after a complete byte scan;
- the ESP32 dump produced a complete FreeRTOS marker scan plus six ESP partitions and 47 NVS entries. Its static
  bytes declare Flash Encryption, Secure Boot and anti-rollback disabled; that is not a live eFuse measurement;
- the encrypted GE800 OTA exposed an AES 128-bit IV, a bounded 64 KiB body sample at 8.00 bits/byte and an honest
  unrecoverable-without-key result;
- the Xiaomi 2018 dump yielded a complete six-variable U-Boot environment and a netboot finding. Other U-Boot
  negatives retained their exact full/prefix coverage;
- the GL.iNet FIT/UBI path yielded its selected IPQ5332 board tree, while the Tenda raw scan yielded two AK3918
  board trees. BeanView and IMOU produced complete, explicit no-valid-FDT results.

Forcing the RTOS provider over every family also found two weak-marker false positives outside normal W0 routing:
`riot` appeared in compressed GL.iNet bytes and `mbed` was a substring of U-Boot's `CONFIG_OF_EMBED` in Tenda.
Both core fingerprinting and W7 now require runtime-specific RIOT/mbed markers; the real samples no longer produce
those findings, while the two eCos images and the ESP32 FreeRTOS result remain unchanged.

The team volume contains no vendor FreeRTOS ELF or matching RAM snapshot. The ESP32 file is a raw flash dump, so it
proves the static FreeRTOS/ESP layout evidence but cannot drive the task-list walker; raw images and the structurally
invalid ELF-looking region in that dump are refused by the symbol resolver. The Pico sample is an RP2350 RISC-V
PICOBIN despite its filename. W7 now validates the block structure before asserting that identity: item sizes,
LAST's preceding-word count, end marker and relative links must agree. On the real sample it followed the complete
two-block loop (offsets 20 and 242436), decoded IMAGE_TYPE `0x1101`, entry `0x10000036` and initial SP
`0x20082000`. These are static declarations in the firmware, not execution or RTOS proof.

The dedicated RISC-V follow-up maps that XIP entry to file offset 54 and asks radare2 to recover only the declared
entry function, avoiding whole-raw-image auto-analysis over data. On the team sample it decoded 37 instructions in
10 basic blocks. FirmLab stores the bounded instruction/CFG inventory and its exact scope; it does not present that
single function as whole-image coverage or as runtime/peripheral evidence.

### Reproduced ST vendor FreeRTOS ELF

The official STMicroelectronics [`STM32N6-GettingStarted-Audio` v2.3.0
release](https://github.com/STMicroelectronics/STM32N6-GettingStarted-Audio/releases/tag/v2.3.0) ships source and
FreeRTOS HEX binaries for STM32N6570-DK, but no ELF. Its documented `make freertos` target was rebuilt with the
documented Arm GCC 13.3.1 toolchain. The release Makefile also passed `-fcyclomatic-complexity`, which that compiler
does not recognize; the reproducible local build removed only that reporting flag. The release asset matched its
published SHA-256 `650e5d5a…edee`; the resulting ELF is `0c825b05…c700`, ELF32 ARM Cortex-M55, statically linked,
with DWARF and not stripped.

FirmLab examined all 29 sections, all 4315 static symbols and the single program header. It resolved 10 of 11
FreeRTOS names, including `pxCurrentTCB`, the 56-entry `pxReadyTasksLists` array, both delayed lists, pending,
suspended and termination lists, and `uxTopReadyPriority`; only the SMP `pxCurrentTCBs` name is absent. The
1120-byte ready-array symbol independently agrees with 56 × 20-byte `List_t`, matching the vendor configuration
(`configMAX_PRIORITIES=56`, 32-bit ticks, mini list item, no integrity words and generic priority selection).
These are complete link-time facts, not a RAM/task-state claim.

The ELF is retained only in the ignored local path
`data/research/vendor-freertos/stm32n6-audio-v2.3.0/GS_Audio_N6.elf`, alongside its license and exact provenance.
SLA0044 restricts executing the proprietary components to ST hardware, so FirmLab will not boot this image under
Renode. A static-analysis regression found here was fixed: a top-level structurally valid ELF now outranks
incidental SquashFS magics inside its debug/section bytes and routes to W7 rather than Linux extraction.

Pending: a matching RAM snapshot captured from STM32N6570-DK hardware, a 64-bit-tick runtime fixture, RISC-V
analysis beyond the now-validated entry function (bounded reachable-call discovery without raw-data false
functions), and a suitable runtime or peripheral model.

## Kernel CVE backports

Primary sources: the [Linux kernel CVE process](https://docs.kernel.org/process/cve.html), CVE Services/CVE List
v5 records, Git's [`patch-id` documentation](https://git-scm.com/docs/git-patch-id) and official vendor
documentation from Red Hat/SUSE on backported fixes.

For `CVE-2026-43286`, the official Linux CNA record named the affected file, introducing commit and three stable
fix commits. The three official patches produced the same `git patch-id --stable`, demonstrating that equivalent
backports can be recognized across different commit hashes.

That result proves only that a source tree contains an equivalent diff. It does not prove that the tree produced
the kernel bytes in an analysed firmware image. The defensible MVP is a bounded, read-only comparison against an
operator-provisioned local mirror. It is now implemented as a pure CVE 5.x Linux-CNA parser plus a local Git
comparator. The parser was checked against the live official `CVE-2026-43286` record, including its three closed
Git ranges and one open Git introduction. Synthetic repositories cover exact ancestry, equivalent stable patch-id,
partial mismatch, dirty/non-Git trees and missing objects. Every result fixes `artifactBinding: unverified` and
does not change `ProofState`.

`POST/GET /images/:id/kernel-backport` now validates the local absolute mirror path, CNA record and numeric bounds
before creating a durable job. The stored job parameters omit the full CVE document, and the result is not synced
as a finding. The findings read path joins up to 128 durable results, newest first per CVE, under optional
`evidence.backportEvidence`; old results without `cveId` remain valid and unattached. The join never changes
severity or `ProofState`. Resolving the firmware's patch state still requires a reproducible binding of source,
configuration and toolchain to the extracted kernel artifact.
