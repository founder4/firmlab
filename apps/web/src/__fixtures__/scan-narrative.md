GL.iNet-BE3600_4.9.0.bin is an arm64 OpenWrt-style FIT container wrapping a UBI image. The single-pass extractor returned zero files; the rootfs only appeared after a manual carve through the FIT sub-images, then UBI volume selection (the largest of two SquashFS volumes, `ubi_rootfs` at 97 MB), and finally a SquashFS mount. That rootfs became the basis for all subsequent analysis.

The firmware carries a total of 725 findings: 55 critical, 199 high, 224 medium, 26 low, and 221 informational. Of the critical items, four are **static_confirmed** and can be traced as a full source‑to‑sink chain; the remainder are unproven leads awaiting runtime reproduction.

The most impactful chain is a **command injection** in the Tor module. Web-taint tracing shows that the `params.enable` parameter feeds an os.execute call that constructs a shell command from a UCI value without sanitisation, resulting in root‑level command execution via the uCI→shell path. The engagement vector is **web‑origin → uci → os.execute → shell → root**. Two additional **config-restore bypass** findings share a similar structure: the Tor and WireGuard (`wg_client`) modules each read a UCI value and pass it directly to os.execute or io.popen. Because the uCI restore process imports configuration without running the RPC-layer validator, an attacker who can write to a config file can achieve arbitrary root execution by restoring a malicious configuration. Both are static‑confirmed.

A third static‑confirmed critical finding is a hardcoded empty password for the `root` UID‑0 account. This is a direct authentication bypass to the device’s operating system; no exploit chain is needed beyond network access to a login service.

The remaining critical findings (CVE-2022-48174 in busybox 1.36.1, CVE-2024-5535 and CVE-2025-15467 in OpenSSL 3.0.13, and CVE-2025-4517 in Python 3.11.7) are reported by the SBOM worker but are tagged **needs_runtime_reproduction** — the static fingerprint identified the package versions but the analysis does not demonstrate a live exploit path on this particular firmware.

Four stack‑overflow candidates surfaced in the binary‑vuln sweep (400 ELFs). On three of those binaries (`dhcpdiscover`, `dumpimage`, `mkimage`), symbolic reachability with angr was **inconclusive**: the budget expired before any sink could be proven reachable from the entry point. These leads remain **unproven**; the absence of a reachability proof does not mean the sink is unreachable. The fourth candidate was left as a stand‑alone unproven lead.

No NVRAM key‑value store was found in the scanned partition bytes, but the scan caveat notes that a vendor‑specific store behind an unknown header, or one held in a file, would have been missed. Similarly, the kernel posture worker answered only 1 of 9 questions definitively, leaving 8 undetermined.

In summary, the most actionable finding is the set of static‑confirmed command‑injection paths via UCI‑backed shell execution, which together with the empty root password provides multiple avenues for full device compromise if the attacker can reach the web interface or inject configuration. The firmware also contains a large SBOM‑derived CVE footprint, but none of those are experimentally validated in this analysis.
